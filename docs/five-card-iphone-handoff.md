### 从你的电脑开始

朋友用 Windows 时按下面的 PowerShell 步骤起步。你可以独立完成 USB 读盘、桌面 BLE 文件下载、哈希核对、上传与重传验证，并在自己的 iPhone 上使用官方 App。自有 iPhone 客户端的源码可以在 Windows 上编辑；把源码和样本记录交给项目负责人的 Mac，由双方用完整 Xcode 构建、签名、安装，再在 iPhone 上测实际的后台行为。[Apple Xcode 系统要求](https://developer.apple.com/xcode/system-requirements)

1. 在 PowerShell 中运行以下命令。如果已有项目副本，只需进入项目目录。确认 Windows 蓝牙已开启，电脑有可用的 BLE 适配器。USB 线连接时先用资源管理器核对录音卡的盘符和 `record` 文件夹。

```powershell
git clone https://github.com/sunruize93-cmyk/anc-card.git
Set-Location anc-card
Get-Volume | Select-Object DriveLetter, FileSystemLabel, FileSystem, SizeRemaining
```

2. 把一条自制 WAV 从卡复制到本地私有测试目录后记录大小和哈希。下面的路径由文件选择者输入，可直接粘贴资源管理器中的完整路径。

```powershell
$wav = (Read-Host '本地测试 WAV 的完整路径').Trim('"')
(Get-Item -LiteralPath $wav).Length
(Get-FileHash -Algorithm SHA256 -LiteralPath $wav).Hash.ToLowerInvariant()
```

3. 安全弹出后拔线并唤醒 A 卡。在 Windows 的 Edge 或 Chrome 打开[厂商 BLE 测试页](https://nextproto.top/qs668/)，点连接，在系统选择器中选 A。先读电量和固件，再列文件、下载新口令、播放并核对大小。设备未出现时，先让其他手机或浏览器断开该卡，检查系统蓝牙、适配器驱动及浏览器授权。USB 样本可先供队友做转写对照。
4. 厂商测试页足够时直接使用。若需可重复的桌面下载工具，可在 Windows 原生 Python 环境使用 Bleak 的 WinRT 后端实现第 2 节协议并记录结果。退出桌面连接，再让 iPhone 接管同一张卡。[Bleak Windows 文档](https://bleak.readthedocs.io/en/latest/backends/windows.html)
5. 若朋友也有 Mac，可直接在该机继续。用 Finder 复制 WAV，用 `shasum -a 256 "/实际路径/样本.wav"` 核对原件。负责构建的 Mac 先检查 `xcode-select -p` 和 `xcodebuild -version`，选择与 macOS、手机系统匹配的完整 Xcode。现场准备测试 iPhone 的信任、开发者模式、签名团队和唯一 Bundle ID，先编译运行最小 App，验证蓝牙授权。
6. 从 Windows 向 Mac 交接时，提供分支和提交号（或源码包）、运行说明、同一测试文件的哈希及 BLE 返回码。Mac 打开相同版本，现场真机执行第 4 节。若当天 Xcode 或签名尚未就绪，先交付五卡表、官方原稿、桌面下载和后台上传实测；“自有 iPhone 前台 / 锁屏 / 离线恢复”分别保留为待测。

- [ ] Codex 先查看已有代码；沿用已有 iOS 目录或新建最小 Swift/Core Bluetooth 客户端。每次实测注明发送端是 Windows、Mac 或 iPhone。现场人员负责解锁手机、授权、操作机身按键。源码与可复用说明放仓库，原音、逐字稿、设备标识及凭证留在私有目录。
- [ ] 对接人提供实际 HTTPS 地址、短期绑定凭证及样例回执。先把桌面取回的文件用双方约定的字段发送一次，核对录音 ID 和哈希，然后重传同一文件；手机端独立重复这轮验证。后台 SpeakMode、百炼和飞书继续在项目负责人的 Mac 环境运行。

## 2 · 实现前台取回，先交出一条可播放文件

- [ ] **读设备。** 发现 AE20 服务。AE21 写入，AE22 回应命令，AE23 通知机身事件。分别订阅两条通知并分别缓冲组帧。实现帧长和 CRC 校验。按公开协议发送容量 0-1、电量 0-3、固件 0-10、录音状态 3-19。电量 110 表示充电中。
- [ ] **发现新录音。** 首次绑定保存文件列表基线。用 2-0 列文件，接收多条 2-1，记录结束通知或兼容超时。按键保存事件触发重新列文件，重连时再对账，补回手机不在附近时的新录音。将已存在文件和本轮新增文件区分开。
- [ ] **传文件。** 检查当前连接对 withoutResponse 的最大写入长度及可写状态。2-2 下载请求为完整 36 字节，一次写 AE21。文件名截断时按协议恢复扩展名。收到 2-3 后拼接 2-4，2-5 完成码为 0 时结束。先保存临时文件，校验后再作为完整文件入队；需要换后缀时保留原错误和已收字节。
- [ ] **校验。** WAV 查 RIFF/WAVE、声明长度、采样格式与时长，计算收到文件的 SHA-256，并播放首尾。卡内列表的压缩体积可能与下载得到的 WAV 不同。裸 OPUS 保留格式记录，交给队友协商解码；当前后台接受 64 MiB 以内的 WAV/M4A/MP3。
- [ ] **交接点一。** 给队友一条编号明确的测试文件及其字节数、哈希、时长、来源卡、固件。附简短日志“保存事件 → 列表新增 → 下载结束 → 本地落盘”。[厂商公开协议、帧格式与返回码](https://github.com/nextproto1024/ai-recorder-card-open-protocol/blob/main/docs/protocol.zh-CN.md)

[ ] **开流。** 拔掉 A 卡数据线、唤醒设备，用 Windows Edge/Chrome 打开[厂商 BLE 测试页](https://nextproto.top/qs668/)，选中目标卡并启动实时音频。若用 Bleak，先订阅 AE22，按协议发 `1-0`，记录开始响应中的文件名，连续接收 `1-1` 的 Opus 数据。实时数据和卡内文件下载是两个不同命令。原始帧保留到私有目录，使用厂商提供的封装工具生成可播放的 Ogg/Opus，或解码为 PCM。[协议与工具](https://github.com/nextproto1024/ai-recorder-card-open-protocol)
2. [ ] **连续录约 10 分钟。** 开始时念“开场一”，中间定时念时间口令。确认结束前已经收到音频帧，并能解码听到口令。记录首帧延迟、已收帧数和解码时长。用单调时钟测耗时，记下首尾采样位置供后台定位。
3. [ ] **制造一次真实断连。** 念“断前二”，主动断开 BLE，保持卡开机；断开期间念“断中三”。记录最后一帧时间。重新连接同一张卡并重新订阅，按设备实际状态恢复推流，念“恢复四”。记录自动或手动恢复、首个可解码帧时间及中断秒数。同一测试会话下分段保存，以缺口标出两段间隔。
4. [ ] **结束并核原件。** 用 `1-2` 结束实时音频，查卡内列表。若有本轮原件，下载后对照四个口令，核实能否补回断中内容；若设备在断开时停止录音，记下最后可听位置。通过条件是断开前后都有实录可播放，缺口可定位、恢复后顺序正确。离线补回的内容标明补回时间。
5. [ ] **交接并共同验收。** 给队友两段音频的私有位置、哈希、口令位置、缺口及重连日志。若后台实时入口可用，使用这张卡再实录“一条交办 → 改要求 → 撤回”，观察实时音频到原卡回写。无论哪种输入，最后一起打开真实飞书测试群：记下首次派发的任务 ID 和消息 ID，观察修改和撤回都更新原卡，旧确认无法启动任务。队友从后台核对版本与执行次数。使用模拟输入时，在结果中写清来源。

## 3 · 官方 App 转写质量

通过[厂商产品页的官方 App 使用指南](https://nextproto.top/products/ai-record-card)找到“声云语音转写”。在 B 卡记录 App 实际采用的是卡内文件同步、导入还是实时转写。保留版本、语言、降噪/分角色设置、原始逐字稿、录音保存时间、成稿时间和导出选项。逐字稿无法导出时，在设备上保存完整可读的分屏截图或逐段抄录，注明获取方式。若遇付费限制，记录具体受限步骤。

优先用 B 卡为 Q1–Q3 各录一次。先保存每条卡内原件，再让“声云语音转写”通过它实际支持的入口处理同一条卡内录音；自有路线读取这条录音并交给 SpeakMode＋百炼。官方 App 支持文件导入时，两边直接使用同一 WAV，并核对 SHA-256。官方侧拿不到输入哈希时，用卡号、卡内文件名、时长和首尾口令核对，标记“同次录音，官方输入字节未核实”。如果官方仅支持实时识别，两张卡并排同时收同一段播放，固定音量和距离，标记“双设备同场”；这种结果单列。手工导入可以完成质量比较，自动同步另用新录音验收。

## 4 · 自动上传和 iOS 后台恢复

双方开工时确认一份测试接口。以下是移动端拟定约定，后台负责人提供实际 HTTPS 地址和按设备绑定的短期测试凭证。当前 Mac 本机接口是 `POST /api/recordings`，监听 `127.0.0.1:4785`，返回 `{duplicate, recording}`。iPhone 鉴权入口已接通：`POST /v1/recordings` 收原始音频字节，返回录音 ID、哈希、大小、去重标记及结果查询路径；局域网地址与设备凭证私下交付。

| 客户端发什么 | 服务端怎样答 | 两端怎样判断完成 |
|---|---|---|
| 磁盘文件原始字节、绑定标识、稳定的本地录音标识、文件名、字节数及 SHA-256；有可靠的录音时间才附上时间与来源 | 示例回执 `{"recordingId":"…","bytes":440364,"sha256":"…","duplicate":false}`。服务端从凭证确认成员，核对字节后持久化并入队才返回回执 | 手机核对字节数及哈希并保存 ID。同一绑定重传同一条录音返回原 ID；跨绑定分别保存来源。丢回执时保留文件并重试 |

- [ ] 在手机持久化卡绑定、源文件标识、落盘路径、SHA-256、传输状态、尝试次数和上次回执。下载中断后按实测支持的偏移恢复，或重新完整下载。保留唯一待上传记录。
- [ ] 前台先用一条新文件打到真实 HTTPS 接口；模拟服务器已接收而手机丢失回执，确认重传得到同一 ID。权限失效时显示可处理的错误并保留文件。测试设备同 Wi-Fi 和断网恢复。手机只持有自己的上传凭证。
- [ ] 启用 Core Bluetooth 的 bluetooth-central 后台模式和状态恢复；使用稳定标识的后台 URLSession，从已落盘文件发起上传。绑定与首次授权完成后，再开始计时。自动下载、上传与回执都要能关联到具体录音。[Apple 蓝牙后台说明](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html) · [Apple 后台文件传输](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)
- [ ] **交接点二。** 先约定观察窗口。分别在 App 前台、iPhone 正常锁屏、无网络后恢复三种状态各录一条新口令，记录机身保存、iPhone 落盘、后台持久化三个时间，锁屏期间保持屏幕锁定。上传完成由后台同事观察。强退、系统蓝牙开关、重启首次解锁单独记结果。[Apple 蓝牙恢复条件](https://developer.apple.com/documentation/technotes/tn3115-bluetooth-state-restoration-app-relaunch-rules)
- [ ] 两部 iPhone 分别绑定 A、B，同时录不同口令。核对两条回执对应正确人员，重新打开 App 后绑定仍正确。再对 C–E 做前台短录回归。只有一台手机时先逐卡核对，并把双手机并发留为待测。
