# ANC Card 录音卡到货后的测试清单

整理日期：2026-11-12。先用一个人、一张卡、一个接口任务和一个飞书测试群，逐段验收，再扩大到长录音和五人协作。每个方框都表示待执行的检查，本清单不代表已完成真机验收。

目标流程：录音结束 → iPhone 自动同步与缓存 → 直接上传后台 → SpeakMode＋百炼 → 带原音频时间范围的行动项与统一台账 → 飞书负责人确认 → Agent 执行与独立验收 → 同任务续跑和原卡片更新 → 核对后沉淀知识并用于下一轮。

## 开测前先确认范围

| 环节 | 当前基础 | 到货后要补齐或实测的部分 |
| --- | --- | --- |
| iPhone 自动同步 | 已核对公开 BLE 协议和 iOS 后台机制 | 同步客户端、实际固件兼容、锁屏取文件与后台上传 |
| 手机上传后台 | 现有网页支持本机手动导入 | 手机可访问、有身份验证的上传入口、设备与成员绑定；现有 `127.0.0.1:4785` 不是手机公网入口 |
| SpeakMode 与台账 | 已有短样本真实云端结果及队列恢复检查 | 使用录音卡实际采集的新音频重验，不用缓存或协议夹具代替 |
| 飞书 | 已有音频收件、任务卡片和回调代码及离线检查 | 配置测试群与负责人；补齐并验证 iPhone 直传后台后的自动结果发卡 |
| Agent 执行 | 已有接口与 429 场景的 Codex 两轮执行及会话持久化 | 真实群确认、同会话续跑与原卡片回写；通用 Personal Agent 调度仍待开发 |
| 知识反馈 | 已确定目标和职责 | 纠正记录、知识版本与下一轮检索引用仍待开发 |

手动分享只用于定位故障。通过手动分享跑通下游时，可记录“下游单独通过”，iPhone 自动同步这一项仍保持未通过。

## 验收记录规则

每条用例记录“未测、阻塞、失败、通过”之一。依赖未实现时标阻塞，不填通过。上一段通过后再测下一段；失败时保留数据，修复后重跑失败项及受影响的后续项。

首次授权、绑定设备和设置测试群可以手动完成。进入日常流程后，从按卡保存录音到飞书出现结果卡之间不应再点同步、导出、分享或刷新。负责人核对方案与授权执行仍是预期操作。

对主流程做连续三次独立录音，包含至少一次全程锁屏；这三次只是首轮验收样本。开测前填写短录音最长观察窗口和允许人工操作，超过窗口仍未完成就记失败，不通过事后延长窗口修改结论。

## 测试准备

- [ ] P01 记录卡型号、固件、设备标识，iPhone 型号与 iOS 版本，同步 App 版本，后台部署和 Git 提交号。确认实际设备与协议适配，不能只凭商品页判定。
- [ ] P02 完成一次蓝牙授权和设备绑定，建立“测试成员 → 卡 → 手机 → 飞书确认负责人”的对应关系。不要仅按同名显示名自动认定身份。
- [ ] P03 准备手机可访问的 HTTPS 后台与上传身份验证。确认授权上传可持久化、无效身份被拒；不要把现有无手机鉴权的本机服务直接开放到公网。
- [ ] P04 百炼 Key 和飞书应用凭据只在本机或后台配置。选定唯一测试群、负责人和独立测试工作目录，准备已登录的 Codex 执行环境。
- [ ] P05 准备本轮记录表，填写 Wi-Fi／蜂窝条件、最长观察窗口、执行负责人和证据保存位置。网络与转写、执行调用都使用测试样本。

每次录音前写下人工参考文本。首个执行样本读下述内容，读完可留几秒停顿，总长约 30 秒，以实际文件时长为准：

> 由Zoty负责接口示例和调用说明。接口遇到四二九时只重试一次，并用测试验证成功恢复和再次失败。截止时间是本周五。

Q1 由 Zoty 负责，确认按钮绑定 Zoty 在测试群的成员账号。截止时间先保留原文“本周五”，若转成日期，另外记录录音日期、时区和解析依据。第二个样本用普通讨论和无分工内容，检查系统是否误建行动项。

## 第一阶段 iPhone 自动取回录音

本阶段通过标准：只操作卡完成录音，手机自动发现新文件、完整落盘且可播放。

- [ ] S01 前台基线。同步 App 在前台时录一条新音频，仅在卡上保存。检查新录音被自动发现，手机显示明确的下载与完成状态，文件能从头到尾播放。
- [ ] S02 正常锁屏。先完成连接，再锁屏，然后开始并结束一条新录音。保持手机锁屏，检查传输事件与后台收件时间，证明同步不是解锁后才补做。若当前只能解锁后同步，此项记失败。
- [ ] S03 切到其他 App。录音前将同步 App 切到后台，正常使用其他 App，检查录音保存后是否自动取回，是否漏掉录音结束通知。
- [ ] S04 离开范围后补同步。手机离开卡的蓝牙范围时保存两条录音，回到范围后检查是否自动重连并补齐两条；不能只同步最后一条。
- [ ] S05 下载中断。取文件时断开蓝牙再恢复。检查恢复下载或明确安全重下，最终文件完整，临时残片不进入转写；不要把支持恢复等同于已经实现字节断点续传。
- [ ] S06 生命周期恢复。分别测强退 App、在设置中关闭再开启蓝牙、手机重启后首次解锁。记录每种状态能否自动恢复、是否需要重新打开 App、是否丢失待同步录音。恢复限制单列，不能替代 S02 的正常锁屏要求。

保留证据：卡上文件名、保存时刻、蓝牙发现／重连／文件落盘事件、手机导出后的文件时长与字节数、锁屏期间后台实际收件时间。

若本阶段失败，先核对文件列表、通知订阅与下载命令。公开协议要求 `2-2` 下载请求完整 36 字节一次 GATT 写入；测试客户端的实际写入上限和目标固件应满足此要求。校验 WAV 文件头和实际长度；卡内压缩文件大小不能直接作为转码后 WAV 的预期大小。[录音卡协议](https://github.com/nextproto1024/ai-recorder-card-open-protocol/blob/main/docs/protocol.zh-CN.md)

iOS 蓝牙恢复取决于系统状态、待处理事件及目标版本，iOS 26 还涉及 AccessorySetupKit 的相关条件。因此 S06 按实际系统和接入方式分别记录，不统一承诺强退后必然自动恢复。[Apple 恢复规则](https://developer.apple.com/documentation/technotes/tn3115-bluetooth-state-restoration-app-relaunch-rules)

## 第二阶段 自动上传与持久化排队

本阶段通过标准：手机直接交付后台，后台在确认接收后已有可靠记录，失败后可恢复，同一字节内容不重复创建录音。

- [ ] U01 自动上传。手机文件落盘后自动上传，后台保存原音频和排队记录，再返回持久化成功回执。核对手机上传前文件与后台原文件的 SHA-256 完全一致；规范化音频单独校验，不拿它与原文件作字节比较。
- [ ] U02 断网恢复。文件下载到手机后断网，确认本地待上传记录与文件保留；恢复网络后自动补传。不能只在内存里保存待上传任务。
- [ ] U03 上传中断和回执丢失。分别测试中途断网、后台已接收但手机未收到成功回执。重传后复用原录音，不产生多条任务。只对相同字节验证现有哈希去重，换封装或重编码后的内容去重另行定义。
- [ ] U04 并发重复。对同一文件同时发起两次授权上传，核对只产生一条录音记录、一组行动项和对应任务 ID。
- [ ] U05 重启恢复。在录音已排队及正在转写时分别重启测试服务。确认未完成工作恢复，完成项 ID 保留，原音频和已完成分段不丢失。
- [ ] U06 上传边界。空文件、损坏文件和超过当前容量上限的文件应明确报错，不能显示成功或静默截断。有效的小文件随后仍能进入队列。

保留证据：手机上传任务标识、SHA-256、后台录音 ID、持久化回执、状态变化及重启前后记录。后台上传从手机已落盘文件发起，并单独验证系统安排的实际传输时机。[Apple 后台传输](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)

## 第三阶段 SpeakMode 与百炼真实转写

本阶段通过标准：新录音确实经过指定转写服务，保留原文、可核验来源与原音频时间范围。

- [ ] T01 真实调用。选用本轮卡录制的新样本，确认实际执行 SpeakMode `file_asr_lab`，通过百炼得到结果，记录模型、处理批次、分段哈希和回执。协议夹具、旧缓存和飞书自带转写不计入此项。
- [ ] T02 原文核对。回听后核对“负责人、事项、四二九仅重试一次、截止时间”。识别错误保留原始文本并另记纠正，不能覆盖原文后宣称识别正确。
- [ ] T03 分段失败重试。让一个分段发生可控失败，再恢复服务并重试。确认失败可见，已落盘成功分段被复用，未完成分段继续处理。远端请求已处理但回执未落盘时可能重复调用，记录实际请求，不承诺费用绝对只发生一次。
- [ ] T04 时间范围。为每条行动项回听原音频对应区间，核对范围包含那句话且没有越过文件末尾。当前范围来自音频分段，不填写虚构的词级或句级时间戳。
- [ ] T05 非任务录音。使用普通讨论、纯静音或没有明确负责人的内容。检查无任务时能正常完成，模糊内容留待核对，不擅自分配执行。

保留证据：原音频、人工参考文本、未改写的转写、纠正记录、真实 SpeakMode 回执、分段起止位置和原音频回听结果。

## 第四阶段 行动项进入同一任务台账

本阶段通过标准：来源可追溯，分工和确认身份明确，重复处理保持任务身份。

- [ ] L01 候选任务。核对样本只产生预期行动项，事项、口述负责人、截止时间和证据原文正确，初始为待核对。口述“Zoty”与实际飞书确认人之间有明确绑定。
- [ ] L02 来源一致。从任务可以查到本次录音 ID、分段起止时间和证据；重新载入台账或重复上传后仍是同一任务 ID。
- [ ] L03 执行范围。为接口样本准备当前支持的两轮方案并绑定测试负责人。检查首轮与完整任务验收条件均清楚；其他任务类型保留待核对，不硬套接口方案。

保留证据：录音 ID、行动项 ID、任务 ID、负责人绑定、建议 ID、任务版本和验收条件。

## 第五阶段 飞书自动通知与负责人确认

本阶段通过标准：iPhone 直传的录音自动得到结果卡，只有绑定负责人能授权执行，重复操作不重复派发。

- [ ] F01 自动结果卡。使用从 iPhone 直接上传后台的录音，检查处理完成后测试群自动出现来源、分段时间和候选行动项。不能用“先手动把音频发群里再回复”的路线替代。
- [ ] F02 真实回调。负责人核对执行方案后，在真实测试群点击确认，检查平台回调、持久化确认记录和入队结果。确认前没有启动 Codex 执行。
- [ ] F03 身份和版本校验。由另一测试成员点击，或使用旧建议版本／错误任务绑定，检查操作被拒绝且任务不推进。保留安全的错误结果，不伪造其他成员凭据。
- [ ] F04 重复点击。负责人快速重复点击，或从两端点击同一版建议，确认只派发一次执行。卡片显示已接受或已有新进度。
- [ ] F05 卡片发送或更新失败。暂时制造可控发送错误，恢复后检查待发送结果仍在且能补写；卡片故障不会抹掉任务状态。发送结果不明时先核对远端消息，不盲目重复发送。

保留证据：实际测试群、确认负责人、回调事件、确认范围、任务版本和卡片消息 ID。转写结果卡与执行确认卡可以分开，但分别记录绑定关系；下阶段要求执行确认卡在各轮沿用同一消息 ID。

## 第六阶段 Agent 执行与同会话续跑

本阶段通过标准：在确认范围内执行，验收证据独立，缺口回到同一任务，下一轮沿用会话和工作目录。

- [ ] A01 首轮执行。以真实录音产生的接口任务开始，确认绑定负责人授权后才派发 Codex。检查文件产物、调用说明和独立验收结果写回原任务。
- [ ] A02 缺口建议。当前两轮演示预期首轮得到 2/3，缺口为 429 单次重试。核对建议引用原录音与实际失败项，不能把预期分数直接填成实测结果；若结果不同，记录并排查。
- [ ] A03 第二轮确认与执行。负责人确认补充建议后，检查仍是同一任务 ID、Codex 会话 ID 和工作目录，保留首轮快照，独立重跑验收达到 3/3，执行确认卡原消息 ID 不变。
- [ ] A04 执行中断恢复。在独立测试运行中中断执行服务，确认状态明确、会话和已确认范围保留。检查旧进程已经结束，负责人恢复后沿用原会话；不能同时启动两份执行。
- [ ] A05 拒绝未经确认的扩展。超出当前授权范围的修改保留为新建议；一般录音正文中的任意指令不能直接绕过负责人确认或替换验收标准。

保留证据：两轮确认、Codex 会话 ID、工作目录、独立验收输出、每轮代码快照、同一执行卡片的前后状态。第一轮固定接口演示通过后，仍需另行开发和验收通用 Personal Agent 任务能力。

## 第七阶段 纠正与知识反馈

此阶段依赖尚待开发的知识反馈模块，可先在记录中整理证据，但手工整理不能记为自动闭环通过。

- [ ] K01 记录纠正。对一条转写、分工或验收结论作明确纠正。检查原始证据保留，纠正内容、操作者、原因、时间和版本能追溯。
- [ ] K02 下一轮引用。新建一个确实相关的任务，检查 Agent 自动检索并正确引用经核对的经验及适用范围。保留实际检索和引用记录；人工粘贴旧结论不计为通过。
- [ ] K03 不传播错误。加入一条未核对或已撤回的候选经验，检查它不会当作团队事实直接指导执行；纠正更新后，后续任务不再引用旧版本为有效规则。

保留证据：知识条目与版本、关联任务、核对记录、检索结果和下一轮实际建议。这里验收的是可追溯的经验复用，不把它表述为模型已被训练或效果已普遍提升。

## 第八阶段 长录音与五人扩展

前六阶段的单人录音与执行链路通过后再进入本阶段；知识反馈模块可以按第七阶段单独推进。

- [ ] X01 文件容量。当前单文件上限 64 MiB，长 WAV 可能超过。先实现并验证合适的分批传输或格式转换及原始时间偏移映射，再验收超限场景；完整录音不可静默截断。
- [ ] X02 分级长录音。依次测约 10 分钟、1 小时和实际外出长度的录音；核对尾部也有转写、分段偏移对应整份原音频、没有遗漏或重叠造成的重复任务。记录蓝牙传输、上传、转写耗时与百炼调用量。
- [ ] X03 两人再到五人。先两人两卡并行，再扩五人；检查设备、录音、负责人、Personal Agent、执行目录和会话不串线，个人与团队信息按已设范围可见。
- [ ] X04 常开后台。若验收目标包含个人 Mac 关机后仍可使用，关闭个人 Mac，仅保留已部署的后台和执行服务，重新跑一遍短闭环。没有常开执行节点时，不能把仅转写成功写成完整 Agent 闭环通过。

## 失败时从哪一层查起

| 现象 | 优先核对 |
| --- | --- |
| 卡有录音，手机没有文件 | 设备绑定、保存通知、断连后的列表补扫、36 字节整帧、文件完整性 |

| 有转写，任务错或没有时间范围 | 提取规则、原分段偏移、原文与纠正是否混写、人物绑定 |
| 有任务，飞书没有结果卡 | iPhone 直传后的发卡连接、测试群配置、发送权限、回写重试记录 |
| 点击确认没有执行 | 实际回调、绑定负责人、原卡片、建议版本、执行队列与节点登录状态 |
| 执行后出现新任务或新会话 | 原任务绑定、会话保存、resume 参数、工作目录和中断恢复策略 |
| 完成任务但下一轮没有改进 | 纠正是否核对入库、知识版本、实际检索与建议中的引用 |

## 首轮通过结论

- [ ] 正常使用时，只操作录音卡；三次短录音均自动上传并在飞书得到可追溯结果，其中至少一次全程锁屏。
- [ ] 同一文件重复上传、处理失败和服务重启均不会丢失来源或重复创建任务，恢复后状态一致。
- [ ] 负责人真实确认、Codex 同会话续跑、独立验收和原执行卡片更新均通过。
- [ ] 一次纠正能追溯，并在下一轮相关任务中自动得到正确引用。

前三项通过可记“单人录音与执行闭环通过”；加上第四项才能记“含知识反馈的闭环通过”。任何长会议、五人并发、强退恢复或个人电脑关机场景，分别按本轮实测范围报告。

现有离线检查可用 `npm run verify` 重跑；`node prototype/verify-live.mjs` 会生成自制音频并调用已配置的云端服务，只能辅助核对现有转写链路，不能代替卡 → iPhone 自动同步的实机证据。卡内原录音保留，不在本轮执行删除、清空或固件改写。
