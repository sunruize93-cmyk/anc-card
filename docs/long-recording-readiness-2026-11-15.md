# 11 月 15 日 Coffee Chat：一小时录音接收准备

## 结论

Mac 后台已切换到支持 **256 MiB 单文件** 的版本，适合本卡此前实测的 16 kHz 单声道 PCM16 WAV：一小时约 115 MB。今天主路径是完整录音保存后，通过 USB 复制原音，再在 Mac 导入，异步转写并由现有主机器人更新结果卡。

**这不是一小时蓝牙或锁屏传输实测通过。** 当前已安装 iPhone App 仍有 64 MiB 下载保护；本轮没有更新、重启 App，也没有连接或控制卡。手机端长文件下载及断连恢复仍需单独升级与实测。

## 后台改动

- 主服务、手机 HTTPS 入口和网页选择器统一为 256 MiB；上传窗口为 15 分钟；手机网关同时只接收一个上传，第二个明确返回稍后重试。
- 标准化 WAV 也限制 256 MiB，不因压缩输入较小而无限扩大内存读取。现有 SQLite 原音保存方式仍保留，未来多人并发需另做磁盘流式存储优化。
- 仍按原音位置分段调用 SpeakMode/百炼。成功片段有持久化缓存，失败重试从未成功部分继续；本轮不改变识别模型、任务确认规则或原卡更新机制。
- 本机新增导入脚本，先核对完整原音哈希，再流式提交、比对后台回执，并要求向已配置群发送结果。脚本显示“入队”不代表云端转写已完成。

## 凭证与网络

设备上传凭证已由本机操作者明确续期 7 天，原 token、设备身份、权限范围不变；原配对码窗口没有重新开放。网关每次请求读取本机原子更新的配置，后续续期或撤销不用重启网关。无效 token、到期凭证继续拒绝，配置损坏时不放行。

还发现旧 HTTPS 证书在 11 月 16 日到期。已用原 CA 私钥和身份准备续期证书，并部署新服务证书；新旧 CA 当前均可严格验证服务器身份。更新后的 CA/手机连接配置只保存在私有目录，不进入 GitHub。

Mac 今日局域网地址发生变化，因此旧手机地址也需更新。**手机本地仍保存旧地址、旧有效期和旧 CA；用户录音保存后，再通过 Mac 同步 `device-import.json` 与 `test-ca.der` 并重开 App。** 不得把服务端续期说成手机已自动完成更新。若网络再次变化，先核对新地址和证书 SAN；不要跳过 TLS 校验。

## 用户回来后的操作

1. 卡上确认录音已保存，通过 USB 复制原始 WAV；保留卡上原件和首次导出的原件。
2. 检查文件可播放、总时长接近实际聊天时长、首尾存在；确认格式、大小及哈希。不要把未保存完或半传输的文件当成功原件。
3. 在项目根目录运行（替换真实文件路径）：

```sh
node prototype/scripts/import-coffee-audio.mjs '/absolute/path/coffee-chat.wav' Eric-USB
```

4. 保留脚本返回的 recordingId，在本机录音页跟踪转写、失败原因及飞书投递状态。失败后重试同一录音，不通过改名反复创建任务。
5. 检查飞书结果卡与原音一致、原音时间范围可回听。真实聊天不一定出现系统当前能识别的明确分工；任务为空时先人工核对，不能虚构负责人或承诺。
6. 若要恢复手机上传，再同步新的私有连接配置；升级手机长文件下载应放在本次原音安全导出之后。今天不以升级 App 作为 USB 转写的前置条件。

凭证续期工具（仅本机操作，输出文件含凭证，不可发群或提交）：

```sh
node prototype/scripts/renew-upload-device.mjs DEVICE_JSON HTTPS_BASE_URL 7 PHONE_IMPORT_JSON
```

该命令不更新手机，也不续期 TLS 证书。手机端有效期、服务端有效期、证书和地址应一起核对。
