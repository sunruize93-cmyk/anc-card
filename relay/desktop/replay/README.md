# 离线 BLE 协议回放回归包

给 iOS 侧复用的输入和期望。不连卡、不联网、不上传、不调接口，只用 Windows 桌面工具已有的 Python 环境。

本轮（2026-11-14 下午）修复了上一轮列出的四个已知缺口中的两个：**G2 d**（下载期间的机身保存事件被吞掉）和 **G3 c**（迟到的列表结束帧让下一轮列表错位）。G2 c 和 G3 d 按约定留到下一轮，仍以 expectedFailure 保留。

## 被测的是什么

被测的是 Windows 桌面工具 ancrelay **现有的代码本身**，不是另写的一套假实现：

- `transport.CardLink`：AE22、AE23 分开组帧；应答队列；本轮新增的事件队列。
- 厂商的 `FrameParser`（`third_party/qs668`）。
- `ops.read_status`、`list_files`、`pull_file`、`read_record_state`。
- `cardfiles.pull_new_files` 和 `watch` 循环。

假的只有「卡」：`harness.ScriptedCard` 照 Bleak 客户端的接口做，按 JSON 脚本决定回什么、什么时候回、按什么字节边界拆成几次通知，再从 CardLink 的真实通知回调喂进去。它不替被测代码做任何判断。

## 本轮的修复

### G2 d：机身事件和命令应答分开排队

修复前：`ops.pull_file` 等 2-5 时，从同一个队列里读帧，TYPE 不是 2 的一律丢掉。下载期间到达的 AE23 3-3 就这样被吞了，`watch` 要等下一次轮询才发现第二条录音。

修复后（`transport.py`、`cardfiles.py`）：

1. 帧组好后就分流。AE23 上 TYPE=3、CMD 为 1/3/5/7 的机身事件进**事件队列**；其余帧（包括同样走 AE23 的 0-4 电量应答）进**应答队列**。等应答的代码只读应答队列，碰不到事件。
2. 事件队列容量 16，满了丢最旧的并计数（`dropped_events`）。同一事件在被取走之前重复到达，只算一条，记重复次数。
3. 断开时（主动或意外）清空事件队列；新连接是新的 `CardLink`，不继承旧事件。
4. `watch` 改为等事件：
   - 收到保存事件后先等 `settle_s`，这段时间里又到的保存事件由这一次对账一并覆盖。
   - 对账开始后才到的保存事件留在队列里，下一轮再处理。
   - 空闲时照旧定时对账。
5. 以前 `watch` 空闲时会顺手读掉应答队列里的旧帧，现在空闲时等的是事件。所以每次对账前显式清掉已到达的旧应答（例如迟到的重复 2-5）。列表帧不在这里清，留给 `list_files` 自己处理。
6. 实时推流演练（`drill.py`）原来从读帧结果里记机身按键日志，现在改为从事件队列取。

### G3 c：列表不把旧的结束帧当本轮结束

修复前：`list_files` 发 2-0 前不清队列，应答序号又不可靠。上一轮迟到的 2-18 会让下一轮立刻结束、返回空列表，本轮真正的 2-1、2-18 再错位给下一次调用。

修复后（`ops.py`）：

1. 发 2-0 之前，取出队列里已经到达的旧 2-1、2-18 丢掉。
2. 本轮还没收到任何 2-1 时到达的 2-18，一律当孤立帧，不当结束。
3. 一次列表如果靠空闲超时结束（没等到自己的 2-18），链路上记一笔欠账 `late_list_ends`，因为它的 2-18 可能还会迟到。欠账上限为 1。
   - 有欠账时，本轮 2-1 之后的第一个 2-18 也先当可能是旧的：抵掉一笔欠账，继续收一个空闲周期。
   - 如果这之后靠空闲结束，**不再加欠账**，并在报告里标 `ambiguous_end`：那个 2-18 多半就是本轮自己的。否则上一轮的 2-18 真丢了时，欠账永远清不掉，之后每次列表都慢一个空闲周期（场景 G3 i）。
   - 清掉已排队的旧 2-18、遇到孤立的 2-18，也都抵欠账。
4. 只收到孤立的 2-18、一直没有 2-1：**重试一次**；仍然这样就抛 `ListUncertain`（`CardError` 的子类），**不返回空列表冒充成功**。
   - 长驻的 `watch` 遇到它只记一条 `list_uncertain` 日志、等下一轮对账，不断开重连（否则卡持续只回孤立 2-18 时会不停重连）。
   - 一次性的 `pull_new_files` 调用照常把它抛给调用方。
5. 每次调用的情况记在 `link.last_list_report`（尝试次数、清掉的旧帧数、孤立结束帧数、靠什么结束、是否 `ambiguous_end`）。

断开时尚未处理的机身事件随事件队列一起清掉，不带进新连接；重连后的第一次对账会把这期间的新录音补回来。

没有动的：`pull_file` 的读帧逻辑、厂商解析器、录音状态门禁。

## 运行

在 `relay/desktop` 目录，用已有的虚拟环境：

```powershell
.venv\Scripts\python -m pytest replay -v -rxX
.venv\Scripts\python -m pytest tests third_party/qs668/test_qs668_protocol.py
```

不装 pytest，只用标准库：

```powershell
.venv\Scripts\python -m unittest discover -s replay -t . -v
```

把剩下的两个已知缺口当普通测试跑，看具体失败信息：

```powershell
$env:REPLAY_SHOW_GAPS = "1"; .venv\Scripts\python -m pytest replay -v
```

**关于 asyncio 调试模式**：`unittest.IsolatedAsyncioTestCase` 默认开启调试模式，它会给每个回调和定时器记录调用栈。回放场景里一次下载有几百个通知回调，调试开销会把合成时序拉长好几倍。实测同一个 G2 d 场景，开调试时第一条下载 3 秒内都完不成，关掉后约 0.8 秒。所以回放测试统一关闭调试模式运行（`ReplayCase.asyncSetUp`），和生产运行一致。这个改动只在测试里，没有放宽任何断言或时间期限。

修复前各场景的失败原因（见 `evidence/before.txt` 的断言信息）：

- **G2 d、e、f**：都只下载了第一条，第二条漏了。
- **G3 c、e**：第二次列表返回空列表。
- **G3 g、h**：返回空列表。g 本应报「列表不确定」，h 本应在重试后拿到 1 个文件。
- **watch 不确定**：每次轮询都记 `list_checked total=0`，把不确定当成「卡上没有文件」。
- **G3 f、G3 i 是例外**：修复前列表内容其实是对的，失败只是因为修复前的代码没有 `last_list_report` 字段。它们不能算作修复前行为有错的证据，只是给新的欠账逻辑做回归。

「通过」指的是状态机层面的期望：下载了哪些文件、什么时候、发了几次列表请求、列表内容、是否报不确定、欠账是否清零，不只是 CRC 和长度。

### 单元测试（`tests/test_events.py`，12 个）

AE23 上 0-4 进应答、3-3 进事件；等应答时事件不丢；重复只排一次、取走后再来算新的；不同事件保持到达顺序；容量满丢最旧并计数；等事件超时；主动断开和意外断开都清空事件并让等待者收到断连；新连接没有旧事件；清理旧应答只拿走匹配的、保持其余顺序；被放弃的读取任务手里那一帧也能清掉；事件永远不会被清理应答带走。

## G4 保存后最终可发现性（synthetic）

`test_late_listing.py` 和 `scenarios/g4-late-listing.json`。问题是：3-3 保存事件先到，新文件要再过一到两次列表才出现。

用的是真实的 `watch` 循环加脚本卡。断言看最终结果，不只看日志：
- **落盘文件**：只有新文件一个，字节和 SHA-256 与卡上原件一致。
- **成功次数**：2-2 只发一次，「下载完成」「新写入」各一次。
- **基线**：每 10 ms 采样一次，下载成功之前一直只有旧文件，结束时恰好是旧文件加新文件。

| 变体 | 情形 | 现有版本 582d03f |
| --- | --- | --- |
| A | 保存后两次列表都没有新文件，第三次才有 | pass |
| B | 3-3 重复两次；保存后的对账两次都只收到孤立 2-18，报不确定；下一次轮询恢复 | pass：不确定期间基线不变、没有记成空列表成功，最后只下载一次 |
| C | 3-3 到达时主机正在等一次慢列表，事件还没处理就断连；重连后新文件才出现 | pass：旧事件没有在新连接里被处理（保存事件处理次数 0），重连后靠轮询发现，只成功一次 |

现有代码三种都通过，本轮**没有改被测代码**，只加了测试和回放脚手架：
- `harness.py`：脚本回复可以写 `"default"`，表示这一次按默认行为回。
- `harness.py`：`drops_at_ms` 让卡在指定时刻主动断开。

为了确认断言不是空过，做了两个只在测试进程内打补丁的变异检查：
- 把「列表不确定」当成空列表：B 失败。
- 去掉空闲轮询、只在事件时对账：A 和 C 失败（新文件永远取不到）。

这说明**保存后列表晚出现时，最终能发现靠的是定时对账**，保存事件本身不保证。最坏的发现延迟等于对账间隔（`watch --every`，默认 30 秒）。本轮按要求不加新功能，例如保存后按短间隔再查几次。

## 场景

`scenarios/` 下三个 JSON，字段说明在下表。修好的场景用 `fixed` 字段说明修了什么；仍未修的用 `known_gap` 字段说明，有它就按 expectedFailure 跑。

| 字段 | 意思 |
| --- | --- |
| `on_command` | 主机发某条命令后卡回什么：按第几次调用给一组通知，每条通知有 `channel`、`delay_ms`、`frames`、`split_at`（拆分的字节位置） |
| `card.files` | 列表内容随时间变化：`[{"from_ms", "names"}]` |
| `card.record_state` | 3-20 的值随时间变化（1 录音中，2 未录音） |
| `card.unsolicited` | 卡主动发的通知，例如 AE23 的 3-3；`raw_hex` 可以直接给原始字节 |
| `card.reply_seq` | 应答序号：`echo` 回显请求序号，`zero` 全 0，`scrambled` 打乱 |
| `card.reply_delay_ms`、`list_end_delay_ms_by_call` | 应答延迟；每一次列表的 2-18 额外延迟多久 |
| `card.duplicate_end_after_ms`、`end_extra_delay_ms` | 重复的 2-5、延迟的 2-5 |
| `expect.lists_after_ms` | 某个时刻之后应当发出几次列表请求（用来断言「重复事件只触发一次对账」） |
| `expect.report_last`、`late_list_ends_after` | 最后一次列表的报告字段、结束时剩余的迟到结束帧欠账 |
| `expect.list_error` | 应当报的错误类型（例如 `ListUncertain`） |

脚本卡没写到的命令按 A 卡 V1.0.0 的实测习惯回：0-4 走 AE23，0-2、0-11、2-x、3-20 走 AE22，2-4 每帧 200 字节，2-7 不回。

## 给 iPhone 线的参考

`spec/routing-cases.json` 是一份与语言无关的输入/期望表：12 条规则（R1–R12）、16 个用例（E1–E7 事件路由，L1–L6 列表结束判定，D1–D3 保存后最终可发现性），每个用例写清按时间到达的帧和应有的结果。它不是 iOS 源码的移植，只描述行为。

## 仍未覆盖或未知的

- **G2 c 录音状态门禁**：卡在录音中会不会列出进行中的文件，未知；`watch` 仍不查 3-19。留下一轮。
- **G3 d 解析恢复**：同一通道上残留截断帧头时，后续短应答会被卡住。问题在厂商解析器里，留下一轮。
- **多帧长列表里新旧结束帧交错**：如果旧的 2-18 恰好夹在本轮两帧 2-1 之间，而本轮的 2-18 又在空闲周期之后才到，这次列表可能少后半段。协议没有字段能区分，没有场景覆盖。
- **空卡**：真卡在没有文件时回不回 2-1（例如 count=0），没有实测。如果只回 2-18，本轮规则会把空卡报成「列表不确定」，需要硬件确认后再调整。
- **3-3 早于文件出现在列表里**：如果卡先发 3-3、过一会儿才把新文件列出来，这次对账看不到它，要等下一次轮询。没有场景覆盖。
- 真实的通知分片边界、卡在连接期间会不会发 3-3：未知，需要硬件。
- iOS 的后台、锁屏、系统挂起：这里是 Windows 上的 asyncio 时序，**不代表任何 iOS 后台行为**，也不说明锁屏取音的问题已经解决。
- 各场景的时间都是压缩的合成时序。G2、G3 有绝对时间期限的断言已留余量，但在很慢的机器上仍可能误报。
